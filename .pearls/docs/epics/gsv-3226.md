# git-semver: a released version can be labelled, and the labels are published

> Unit 7 of plan `git-dev-aef7` (record: `mangimangi/git-dev`, `.pearls/docs/epics/git-dev-aef7.md`; the design is in `mangimangi/git-dev`, `.pearls/docs/how-versions-move-design.md`, section "Words and shapes settled on 2026-11-28"). Delivers into `plan/git-dev-aef7`, on top of v0.1.2, which the plan's earlier units in this repository released. Re-check every code reference against the code before using it.

## Problem

Nothing records that a released version should not be used. Seen in one week: medici v0.1.108 could not run `medici init`, and a project pinned to it found out by trying; git-cicd v0.0.1 merged before its verdict; git-cicd v0.0.3 broke its adopters' generated workflows and command lines in a patch release. In each case a fixed version followed, and the bad one stayed installable with nothing to say so. The dependency layer being built (`mangimangi/git-deps`) reads what a publisher says about its releases; git-semver is the publisher's tool, so saying it belongs here.

Separately, git-semver still force-moves a `latest` git tag on the bump-on-merge path (`git-semver` lines 625, 700 and 760 at v0.1.1: `git("tag", "-f", "latest")`). A moved tag makes `git fetch --tags` fail in every clone that holds the old one ("would clobber existing tag"). The owner decided to drop it; the pull request mode already does not move it.

## What already was decided (do not reopen)

- **The word is label.** A released version carries labels; the first one is `defect`. ("Mark", "advisory" and "tag" were considered and set aside; "tag" means a version tag only.)
- **Labels are a file, not git tags.** Version tags are immutable; a label must be correctable and withdrawable, reviewable in a pull request, and carry a reason.
- **The file is `git-deps.labels.json` at the root of the repository's default branch.** Whoever keeps the repository vouches for it. git-deps reads it through git; nothing here calls a platform.
- **A pin is a version and a sha:** a label names the version and records the commit its tag pointed at when the label was made.
- **`latest` is computed** by a reader (the newest version no label rules out), not a tag: git-semver stops creating or moving a `latest` tag on every path.
- The format must be able to carry labels this unit does not define (for example `eol` for a runtime, kept in git-deps's own repository, or a positive one later); a reader must be able to ignore a label it does not know.
- `release bump`, `release publish`, the two release modes and `check-bump` are otherwise unchanged. Coverage stays at 99% or more for `git-semver` and `release`; shell changes come with bats tests; no test reads a token or reaches the network. No vendor-protected file is added, changed or deleted; run `python3 .vendored/check --base origin/plan/git-dev-aef7` before finishing. The version check must pass against `origin/main`: this is a new command, so raise the version by a minor step with its changelog entry.

## What ships

- A labels file with a documented, versioned format
  - vehicle: type: issue
  - source repo: git-semver
  - target repo: git-semver
  - affected surface: `git-semver` (reading and writing the file), `templates/` (a schema or reference for the format), `tests/`, `README.md`, `docs/`
  - shape: `git-deps.labels.json` holds, per released version (and per component for a repository with subdirectory versions), a list of labels, each with the label's name, a reason in one line, the date it was made, the commit the version's tag pointed at, and optionally the version that fixes it. The file states its format version. Reading is strict about structure (a malformed file is an error naming what is wrong) and tolerant about content (an unknown label name or an extra field is kept and ignored). Writing keeps the file stable under version control: sorted, one change per line where it can be, no reordering of what was not touched. The format is documented in the README with an example, as the contract a reader such as git-deps relies on.

- A command labels a released version, and one withdraws a label
  - vehicle: type: issue
  - source repo: git-semver
  - target repo: git-semver
  - affected surface: `git-semver` (new subcommands beside `cmd_tag` and `cmd_released`), `tests/`, `README.md`, `AGENTS.md`
  - shape: A subcommand adds a label to a released version: it refuses a version that has no tag, records the commit the tag points at, requires a reason for `defect`, accepts an optional fixing version (which must be a tagged version higher than the labelled one), and is idempotent for the same label on the same version (the reason and fixing version can be updated). A second subcommand removes a label and says so when there was none. A third lists the labels, for all versions or one, in a form a person can read and, with a flag, as JSON. None of them commits, pushes, tags or needs a token or the network: they change the file in the working tree, and the change reaches the default branch as any other change does. The README shows the whole path for a repository with a protected default branch (run the command on a branch, open a pull request) and notes that the labels file is not one of the configured `files`, so labelling does not ask for a version bump.

- No path moves a `latest` tag
  - vehicle: type: issue
  - source repo: git-semver
  - target repo: git-semver
  - affected surface: `git-semver` (the three `git("tag", "-f", "latest")` calls and the messages around them, `cmd_tag`), `release` (`create_releases` skips `latest`), `install.sh` and `README.md` (anything that fetches from a `latest` ref), `tests/`, `CHANGELOG.md`, `VERSION`
  - shape: git-semver no longer creates, moves or pushes a `latest` tag on any path, and no longer force-pushes tags. An existing `latest` tag in a repository is left alone (deleting it is the owner's choice) and is ignored wherever tags are read as versions. The docs and the installer do not rely on a `latest` ref; the bootstrap instructions name a version or the default branch. The changelog says that `latest` is no longer moved and what a repository that relied on it does instead. `VERSION` is raised (minor).

## Acceptance criteria

- Labelling a tagged version writes the file with the label, reason, date and the tag's commit; labelling an untagged version fails; a `defect` without a reason fails; a fixing version that is not a higher tagged version fails; repeating a label updates it without duplicating; removing it restores the file; shown by tests using local repositories only.
- A file with an unknown label name and an extra field is read without error and written back with both preserved; a structurally malformed file is refused with a message.
- After a bump-on-merge release and after a tag-on-merge release in a test repository, no `latest` tag exists that git-semver made, and no push used force.
- `.vendored/pkg/git-cicd/git-cicd check --setup` passes with coverage at 99% or more for both scripts and the bats tests green; `git-semver check-bump` passes against `origin/main`.
- The pull request into `plan/git-dev-aef7` has a passing `Verdict / git-cicd:verdict`.
- `python3 .vendored/check --base origin/plan/git-dev-aef7` reports nothing.

## Out of scope

- The reader (`git-deps check`, `git-deps latest`), which lives in `mangimangi/git-deps`.
- A git-cicd job that labels a release from the Actions tab (it needs declared secrets installed here; the plan's adoption unit).
- Labels other than `defect` as things git-semver knows how to make; end-of-life data; a stable channel.
- Refusing to install or release a labelled version (git-vendored's and git-deps's part).
